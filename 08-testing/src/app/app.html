1. Why Test, and How to Run the Tests

Tests are code that checks your code. They catch bugs before users do, and let you change things without fear: if you break something, a test fails.

The testing pyramid: lots of fast, small tests at the bottom, a few slow, big ones at the top.

Kinds of tests in this folder
KindChecksToolRun with
UnitOne function or service on its ownVitestng test
ComponentOne component's HTML and clicksVitest + TestBedng test
End-to-end (E2E)The whole app in a real browserPlaywrightnpm run e2e

Test files end in .spec.ts and sit next to the code they test. ng test re-runs them on every save; add --watch=false to run once.

2. Unit Tests with Vitest

The simplest tests: call a plain function and check its result. A test has three steps: arrange (set up), act (call the code), assert (expect(...)).

4. Component Tests

A component test creates the component, sets its inputs with setInput(), reads the rendered HTML, and clicks buttons like a user would. A spy (vi.fn()) records what the outputs emitted.

5. End-to-End Tests with Playwright

E2E tests open this page in a real browser and use it like a person: click, type, and check what appears. They're slower, but they prove all the pieces work together.

  • playwright.config.ts starts ng serve automatically before the tests (webServer).
  • Tests find elements the way users do: getByRole('button', ...), getByLabel('Minutes'). Use data-testid only when there's no better handle.
  • expect(...).toHaveText(...) waits and retries, so there's no need for manual sleeps.
